# Backend Contract Matrix

## Status definitions

- `Confirmed`: the current Go API supports the required end-to-end behavior.
- `Partial`: some behavior exists, but the proposed experience needs an
  additional contract or a reduced MVP.
- `Blocked`: no safe supporting contract exists. Do not build an interactive
  product claim.
- `Static`: no application API is required.

## Confirmed response semantics

- Owned account responses contain a public UUID, full owned account number,
  currency, current posted balance, lifecycle status, and timestamps.
- Recipient resolution contains only masked account number, masked name,
  currency, and receiving eligibility.
- Beneficiary responses contain beneficiary UUID, nickname, masked destination
  number, currency, receiving eligibility, and timestamps.
- Transfer requests use sender public UUID and destination account number.
- Internal transfer responses report `fee: 0`.
- Financial errors use stable codes such as `recipient_not_found`,
  `same_account`, `currency_mismatch`, `account_closed`,
  `insufficient_funds`, and transfer-limit errors.

## Required client rules

- Treat the frontend as untrusted; all authorization remains server-side.
- Never expose internal bigint IDs.
- Never derive receiving eligibility from a stale beneficiary alone. Revalidate
  through the transfer operation and, when appropriate, recipient resolution.
- Never calculate a replacement balance as authoritative after a transfer.
  Invalidate and refetch account and transaction queries.
- Do not optimistically mark a transfer posted.
- Generate one idempotency key when the user confirms a transfer and reuse that
  key for transport retries of the exact same intent.
- Generate a new key after any sender, recipient, amount, currency, or narration
  change.
- Do not store access tokens, refresh tokens, device cookies, passwords, or
  account numbers in analytics payloads or persistent browser storage.
- Treat `404` recipient resolution responses as neutral; do not infer whether
  the account is missing or closed.

## Backend decisions required before blocked features

1. Password-recovery token lifecycle and session revocation policy.
2. MFA enrollment, challenge, recovery-code, and step-up contracts.
3. KYC provider, status model, document handling, and retention policy.
4. Virtual-card provider, card-state model, reveal controls, and PCI boundary.
5. Notification-feed storage, pagination, read state, and preferences.
6. Customer session-listing and individual-revocation endpoints.
7. External transfer rails, fee quotation, pending settlement, and reversal
   semantics.
